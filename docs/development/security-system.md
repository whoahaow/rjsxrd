# Система безопасности и фильтрации

Проект реализует многоуровневую систему фильтрации небезопасных конфигов и генерацию наборов для обхода мобильных белых списков.

## Фильтрация insecure-конфигов

Функция `has_insecure_setting()` проверяет каждый конфиг на наличие параметров, снижающих безопасность. Используется для генерации `-secure.txt` файлов.

### VMess

| Проверка | Параметр | Причина |
|----------|----------|---------|
| Отключение TLS | `security=none` | Трафик не шифруется |
| Принудительный insecure | `insecure=true`, `allowInsecure=true` | Сертификат не проверяется |
| Устаревший режим | `alterId`/`aid` > 0 | Узел живёт на deprecated MD5 id-cycle. У `VMessAccount` в xray нет поля `alterId` (читаются только `id`/`security`/`experiments`), поэтому верификатор значение игнорирует и соединяется с нулевым числом alter ID — правило оценивает развёртывание, а не handshake |

Парсер также валидирует: TLS требует непустой SNI, h2 host должен быть корректным массивом.

### VLESS

| Проверка | Параметр | Причина |
|----------|----------|---------|
| Без шифрования | `encryption=none` (без TLS/Reality) | Трафик открыт |
| Insecure | `allowInsecure=true`, `insecure=true` | TLS-сертификат не проверяется |

Парсер Reality: требует одновременного наличия `sni` и `publicKey`.

### Trojan

| Проверка | Параметр |
|----------|----------|
| Insecure | `allowInsecure=true`, `insecure=true` |

Парсер Reality: те же требования, что у VLESS.

### Shadowsocks

| Проверка | Критерий |
|----------|----------|
| Слабый шифр | Единый список в `security_filter.py` — `rc4`, `des`, `rc4-md5`, все `aes-*-cfb`/`-cfb8`/`-cfb1`/`-ctr`, `bf-cfb`, `camellia-*-cfb`, `cast5-cfb`, `des-cfb`, `idea-cfb`, `rc2-cfb`, `seed-cfb`, `salsa20`, `chacha20`, `xsalsa20`, `xchacha20` и др. |
| Метод без шифрования | `none` или `plain` — xray их загружает, и загружает туннель без шифрования |
| Пустой пароль | Длина пароля = 0 |
| Плагин | Любой plugin-параметр (не поддерживаются) |
| **2022 длина ключа** | Base64-ключ для `2022-blake3-aes-128-gcm` должен декодиться в 16 байт, для `2022-blake3-aes-256-gcm` и `2022-blake3-chacha20-poly1305` — в 32 байта. Multi-key формат `key1:key2` (3x-ui) пропускается — это фича Xray-core, не ошибка. |

**Шифры, которые загружает xray** — `SS_XRAY_CIPHERS`, то есть случаи `cipherFromString`
из `infra/conf/shadowsocks.go` (проверено на v26.3.27):

```
aes-128-gcm, aead_aes_128_gcm, aes-256-gcm, aead_aes_256_gcm,
chacha20-poly1305, chacha20-ietf-poly1305, aead_chacha20_poly1305,
xchacha20-poly1305, xchacha20-ietf-poly1305, aead_xchacha20_poly1305,
2022-blake3-aes-128-gcm, 2022-blake3-aes-256-gcm,
2022-blake3-chacha20-poly1305, none, plain
```

Всё остальное — `unknown cipher method`, то есть падение при загрузке конфига,
поэтому `utils/xray_compat.py` отклоняет такой URL до верификации, а не теряет
вместе с ним всю пачку в batch-режиме. `none` и `plain` в список включены
намеренно: загрузить их xray может, и ловить их должна проверка безопасности, а
не проверка совместимости.

`SS_SECURE_CIPHERS` — это `SS_XRAY_CIPHERS` минус два метода без шифрования.
Наборы лежат в `source/utils/security_filter.py` и читаются через
`is_xray_cipher()` в `protocol_parsers.py`, `vpn_config.py` и `xray_compat.py`;
`xray_tester.py` ничего из этого не импортирует и делегирует парсерам. Оба
парсера — и typed, и legacy — приводят метод к нижнему регистру: xray ищет
имена 2022 в `shadowaead_2022.List` с учётом регистра.

**В каком виде приходит шифр.** `extract_ss_credentials()` — единственный декодер,
и покрыть ему надо четыре формы: `method:password@host:port`,
`b64(method:password)@host:port`, `b64(method:password@host:port)` — это SIP003, где
адрес лежит внутри токена и в URL нет ни одного `@`, — и payload SSR. Третья форма не
читалась до 2026-09-27, а непрочитанное здесь не нейтрально: URL, который декодер не
 прочитал, не получает вердикта, а отсутствие вердикта пайплайн записывает как «чисто».
Туннель со `none` в такой форме попадал в `all-secure.txt` и `ss-secure.txt` и в
безопасный слой SNI/CIDR, тогда как верификатор на этой же строке декодировал
`method: none` и подключался. Фильтр совместимости читает тем же декодером, поэтому
blob с шифром, который xray не грузит, теперь отклоняется по имени, а не уносится в
пачку.

### ShadowsocksR

Конвертируется в Shadowsocks (протокол и обфускация SSR теряются, лог при этом
не пишется). Шифр читается через `extract_ss_credentials()` — тот же декодер,
что и у `ss://`, — поэтому список выше действует и здесь. Это важно:
`aes-256-cfb` был дефолтом ssserver, так что большинство SSR-нод отклоняются
до верификации именно по этой причине.

Payload SSR — это urlsafe base64, и чтение его стандартным алфавитом было не ошибкой,
а порчей: `b64decode` не отвергает `-` и `_`, а выбрасывает их, поэтому сдвигается каждый
задетый байт и шесть полей через `:` перестают быть шестью полями. На 600 сгенерированных
spec-correct payload вердикт по шифру исчезал в 90 случаях — и во всех 90 спрятанный метод
был `aes-256-cfb`, то есть ровно тот шифр, ради которого правило и существует: ноды не
помечались ни небезопасными, ни отклонёнными по имени. Через `decode_base64_token()`
оба написания читаются одинаково, и счётчик обнуляется.

### Имена параметров

Каждая проверка ищет параметр: перед именем стоит `?` или `&`, после значения — `&`, `#` или конец
строки. Раньше часть проверок была простым поиском подстроки по всему URL, и это работало в обе
стороны неправильно: `#node-security=none` помечало рабочий конфиг небезопасным и лишало его
secure-файлов, а `#say-security=tls` в имени наоборот убеждало проверку, что шифрование есть.
Поиск по-прежнему идёт по всей строке — `?security=none` после фрагмента считается параметром:
ошибаться здесь можно только в одну сторону, в незащищённый слой, а не наоборот.

У `vmess://` настройки лежат внутри base64, где граница параметра не работает, поэтому
payload режется по первому `#` или `?` до декодирования (`utils/url_payload.py`).
Декодеры выбрасывают символы вне base64-алфавита вместо ошибки, и без этого среза имя
ноды декодировалось как часть её конфигурации: `vmess://` с `allowInsecure` внутри
payload и именем после `#` считался безопасным. Это единственный случай, где правила о
границе параметра выше мало: у base64-форм имя надо снять до того, как о чём-то судят.

### TUIC

Не поддерживается Xray-core — парсер возвращает `None`. Параметр `skip-cert-verify` считается небезопасным.

### Hysteria

- Hysteria2: верифицируется outbound'ом `hysteria` с `version: 2`, TLS обязателен. Узел с `insecure=1` без `pinSHA256` отклоняется до верификации: xray убрал `allowInsecure`, проверять такой конфиг нечем. `pinSHA256`, который не является 32 байтами hex, отклоняется тоже — xray выкидывает из него двоеточия, декодирует как hex и падает на загрузке конфига, а не на handshake
- Hysteria v1: не верифицируется — xray отвергает `version != 2` на загрузке конфига, поэтому `utils/xray_compat.py` отклоняет такие URL с этой причиной

### Общие проверки

```
verify=0 | verify=false | insecure=1/true/yes/on
```

> **Важно:** `verify=0` проверяется как отдельный параметр URL (regex `[\?&]verify=0`), а не простой substring. Это предотвращает ложные срабатывания (например, `skip-cert-verify=0` не срабатывает как insecure).

### Проверки без TLS

Для VLESS без TLS/Reality: если конфиг `vless://` не содержит ни `security=tls`, ни `security=reality`, он считается небезопасным (plaintext трафик).

## SNI/CIDR-фильтрация

Предназначена для обхода мобильных белых списков (Россия, Узбекистан и др.), где операторы блокируют VPN по SNI и IP-адресам.

**Принцип:** конфиги, направленные на «белые» домены/IP (Avito, Yandex, Mail.ru и т.д.), не блокируются мобильным оператором, так как выглядят как обычный трафик на разрешённые ресурсы.

**Процесс:**
1. Загрузка доменов из `config/whitelist-all.txt` (сотни доменов)
2. Загрузка CIDR-диапазонов из `config/cidrwhitelist.txt`
3. Извлечение host:port из каждого конфига
4. Проверка: совпадает ли host/ip с whitelist?
5. Фильтрация несовпадающих конфигов

**Результат:**
- `bypass/` — SNI/CIDR + security-фильтрация
- `bypass-unsecure/` — только SNI/CIDR (без security)

## Верификация конфигов

### Двухуровневая архитектура

```
Raw-файлы → Верификация → Verified-файлы
  (raw/)                    (bypass-*.txt)
```

1. **Raw** — нетестированные конфиги, результат фильтрации без проверки
2. **Verified** — прошедшие верификацию, отсортированные по пингу

### Режимы верификации

| Режим | Механизм | Скорость | Точность |
|-------|----------|----------|----------|
| Xray-core | Запуск Xray → HTTP через SOCKS5 | 60-120 с | Высокая |
| TCP-ping | Asyncio TCP-соединение к host:port | ~5 с | Средняя |
| skip | Без проверки | 0 с | — |

### Пул портов

Для Xray-тестирования используется динамическое выделение портов в диапазонах:

| Диапазон | Назначение |
|----------|------------|
| 20000-21999 | Параллельное batch-тестирование |
| 22000-23999 | Прокси-цепочки (dialerProxy) |
| 24000-24999 | Персистентные прокси |

Каждый конфиг тестируется на уникальном порту, что исключает взаимное влияние.

## URL Health Report

Автоматический отчёт в конце каждого запуска:

- URL с 3+ последовательными ошибками загрузки удаляются из `URLS.txt`
- Отказ от приватного адреса и вызов без попыток вовсе в этот счёт не входят и строку не удаляют: запрос никуда не уходил, так что ни то ни другое ничего не говорит об источнике (`utils/fetch_outcomes.py`, `utils/url_stats.py`). Каждый называется в отчёте прогона — отказ с хостом и адресом (`fetchers/destination_guard.py`), отменённый вызов с хостом и причиной (`run_condition()` / `report_run_conditions()`). Фетч, сделавший все проверенные попытки и ни через одну не прошедший, — это отказ самого источника, и он стареет: даунгрейды TLS по умолчанию выключены, и доступ цену верификации не покупает
- Конфиги из `servers.txt` с 3+ провалами верификации удаляются
- Топ источников по количеству рабочих конфигов
- Статистика сохраняется в `data/url_stats.json` (gitignored)

## Обработка ошибок

В парсерах Xray-конфигов каждое исключение логируется с контекстом. При ошибке парсинга конфиг не крашит тестирование — он просто отмечается как нерабочий и пропускается.

Потокобезопасность везде обеспечивается через `threading.Lock`.

## Защита от сбоев

Система использует circuit breaker для предотвращения каскадных отказов:

- `CIRCUIT_BREAKER_FAILURE_THRESHOLD = 5` — после 5 ошибок подряд breaker размыкается
- `CIRCUIT_BREAKER_RECOVERY_TIMEOUT = 60` — 60 с на восстановление
- Retry: 2 попытки на конфиг при Xray-тестировании, 5 попыток на GitHub upload
- **CIDR OOM guard:** `load_cidr_whitelist()` автоматически пропускает CIDR-диапазоны с >65536 адресов (предотвращает OOM от случайной /8 или /16 записи)

Временные файлы создаются с `TEMP_FILE_PERMISSIONS = 0o600` — только владелец имеет доступ.

## ManagedProcess — жизненный цикл подпроцессов

Управление Xray-процессами вынесено в `utils/managed_process.py`:

1. Процесс запускается с уникальным конфигом (`tempfile.mkstemp` + `chmod 0600`)
2. При завершении (успех, таймаут, ошибка) — гарантированная очистка временного файла
3. `ProcessRegistry` (`utils/process_registry.py`) отслеживает все запущенные процессы
4. При SIGINT/SIGTERM: `default_registry.cleanup(force=True)` завершает все процессы и восстанавливает proxy env vars

## Реестр процессов

Единый `ProcessRegistry` заменил три старых реестра:
- `_active_testers` (xray_tester.py)
- `_xray_process_registry` (ip_verifier.py)
- `_active_proxy_monitors` (proxy_monitor.py)

ProxyMonitor-инстансы отслеживаются в том же реестре (`register_monitor()` / `_proxy_monitors`) — при cleanup они останавливаются **до** завершения Xray-процессов, т.к. мониторы зависят от SOCKS-порта.

Сигнал-хендлер регистрируется только в `main.py` — xray_tester больше не регистрирует свой собственный SIGINT (предотвращает race condition).

## Валидация URL

Функция `is_valid_vpn_config_url()` проверяет, что строка является корректным VPN-URL:

```python
^(vmess|vless|trojan|ss|ssr|tuic|hysteria|hysteria2|hy2)://
```

Строки, не соответствующие ни одному протоколу, исключаются на этапе подготовки контента.

## Case-insensitive протоколы

Все парсеры и фильтры используют case-insensitive сопоставление протоколов. `VLess://`, `VMess://`, `TROJAN://` и т.д. корректно распознаются и обрабатываются. Ключи дедупликации нормализованы к нижнему регистру, поэтому `vless://host` и `VLess://host` дают одинаковый dedup-ключ.

## VPNConfig dataclass

`utils/vpn_config.py` содержит типизированную иерархию датаклассов для всех поддерживаемых протоколов:

```python
class VPNConfig(Protocol):
    host: str
    port: int

    def to_xray_outbound(self, tag: str) -> Dict: ...
    def to_url(self) -> str: ...
    def dedup_key(self) -> Tuple: ...
```

Это позволяет избежать повторного парсинга URL (особенно для VMess с base64-кодированными JSON) и даёт единую точку расширения при добавлении нового протокола.
